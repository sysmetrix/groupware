# 실제 그룹웨어 연결: 미구현 항목과 검증 절차

## 사용자 확인: 공식 API 없이 진행

2026-10-23 사용자가 그룹웨어 API가 없다고 확인했다. 공식 API 명세 확보를 사용자에게 다시 요구하지 않는다. 다음 구현 경로는 로그인된 화면의 정상 조작을 사용하는 브라우저 자동화다. 메뉴·탭·필터·목록·상세·페이지 이동을 관찰한 뒤 실제로 확인한 요소만 사용한다. 화면에 내보내기가 있으면 필터와 전체/현재 페이지 범위를 검증해 기존 CSV/첨부 처리로 연결한다. 내보내기 존재는 아직 확인하지 못했다.

읽기 성공 기준은 현재 계정·조직·조회 시각·원문 링크·페이지별 건수·최종 페이지 대조다. 세션 만료, 권한 부족, 표 구조 변경, 페이지 이동 실패는 수집 실패로 표시하고 기존 완전한 자료를 보존한다. 이후 초안 저장은 실제 입력 화면과 저장 결과를 확인한 테스트 대상으로 검증한다. 제품 내부 URL이나 저장 동작을 추측해서 구현하지 않는다.

이번 재확인에서 브라우저 작업 공간 목록은 빈 배열이었다. 기존 공간을 사용할 수 없어 화면 자동화 관찰은 재개하지 못했다. 공식 브라우저 제어 복구가 현재 선행 조건이며, API 부재 자체는 자동화 불가능을 의미하지 않는다. 설치 진단·로컬 문서 처리 기능은 계속 사용할 수 있다.

현재 구현에 실제 인증·업무 API 호출은 없다. 다음 계약을 확인하기 전에는 수집된 문자열만으로 URL을 추측하거나 자격 증명을 하드코딩하지 않는다.

2026-10-22에 Windows 화면 제어를 통해 로그인된 홈 → 전자결재 HOME → 미결 탭의 정상 조회를 관찰했다. 실제 화면에 미결 목록과 상신문서 목록이 분리되어 있었으므로, 상신 진행과 내 결재 대기를 구분하는 정규화 상태 `in-progress`를 추가했다. 화면 관찰은 API 계약·서버 권한·전체 건수 검증과 구분한다. 연결 오류와 복구 범위는 [브라우저 진단](browser-recovery.md)에 기록했다.

## 1. 연결 방식 결정

- 공식 API·서비스 계정·내보내기·이벤트 지원과 계약 범위를 관리자/공급사 자료로 확인한다.
- 공식 API가 없으면 권한 있는 사용자 세션의 정상 화면 동작을 관찰한다.
- 브라우저 제어 도구가 작업 공간을 안정적으로 유지하는지부터 검증한다. 제어 중단 요청은 존중하며 다른 도구로 운영 화면 제어를 우회하지 않는다.
- 커넥터 계정·조직·데이터 범위·목적을 명시한다. 인증은 로컬 세션 브로커에서 처리하고 모델·공개 저장소에 전달하지 않는다.

## 2. 대표 읽기 시나리오

각 시나리오는 화면의 시작 상태, 사용자 입력, 완료 조건, 요청과 응답의 구조, 결과 레코드 수, 페이지 범위, 관찰 시각, 서버 권한 범위를 연결해 기록한다.

| 시나리오 | 반드시 확인할 내용 |
|---|---|
| 내 결재 대기 | 메뉴 식별자, 상태 코드, 문서 ID, 결재선 열람 범위, 열람 자체의 읽음 상태 변경 여부 |
| 공지·규정 검색 | 검색 조건, 유효 기간, 문서별 ACL, 첨부 권한, 본문·첨부의 버전 |
| 일정 조회 | 개인/공유 공개 범위, 시간대, 반복 일정·취소 일정 표현, 자원 연결 |
| 그리드 내보내기 | 필터 조건, 전체/현재 페이지 범위, 페이지 크기, 합계와 원화면 비교 |

HTTP POST가 조회일 수도 있다. 요청 이름이나 메서드만으로 부작용 여부를 판정하지 않는다. 수집 자료는 로컬에서 관리하고 공유 전 인증값·개인정보를 제거한다.

## 3. 커넥터 인터페이스 목표

```text
readScope() -> authenticated user, organization, permissions, session expiry
listPendingItems(cursor, filters) -> records, nextCursor, total, observedAt
searchAuthorizedDocuments(query, cursor) -> documents, permissions, versions
listSchedules(range, cursor) -> records with timezone and cancellation state
```

이 이름들은 제안 인터페이스다. 실제 제품 API 이름이 아니다. 결과를 `docs/data-contract.md` 형식으로 정규화하고 출처·조회 시각·권한·버전을 유지한다. 서버 권한을 재검증하지 못하면 실시간 연결 성공으로 표시하지 않는다.

## 4. 필수 실패 시나리오

- 세션 만료 및 사용자/조직 전환 시 작업 중단.
- 403, 부재 문서, 삭제·권한 회수된 문서 처리.
- 페이지 중간 실패 시 부분 수집 명시, 합계·전체 건수 확인.
- 문서 조회 후 버전 변경, 첨부 권한 불일치.
- 일시 네트워크 실패와 실제 빈 결과 구분.
- 제품 업데이트로 경로·필드가 바뀌면 계약 검사 실패 처리.
- 모델 입력으로 들어오는 문서 내 지시문은 실행 명령으로 취급하지 않음.

## 5. 변경 작업은 별도 단계

초안 저장·상신·승인·반려·발송·예약에는 명시적 대상/변경 전후 확인, 사용자 승인, 실행 직전 최신 상태 조회, 중복 방지 키, 결과 조회가 필요하다. 자동 재시도로 중복 상신하거나 결과를 추측하지 않는다. 테스트 데이터와 운영 데이터의 경계를 검증한 뒤 기능을 추가한다.

## 6. 레퍼런스에서 도출한 수집·복구 계약 (설계)

[Microsoft Graph의 delta query](https://learn.microsoft.com/en-us/graph/delta-query-overview)는 빈 페이지에도 다음 링크가 있을 수 있으며 전체 페이지가 끝난 후 후속 동기화 상태를 제공한다. 이를 참고해 다음 기준을 제안한다. Amaranth에 동일 API·이벤트·토큰이 있다는 뜻이 아니다.

1. 페이지 결과를 임시 수집하고 마지막 페이지·중복 ID·표본 합계 검사를 끝낸 뒤 게시한다. 중간 실패나 세션 만료로 모은 부분 자료를 완전한 스냅샷으로 교체하지 않는다.
2. 체크포인트에는 사용자·조직·조회 조건·계약 버전을 묶는다. 자료 확정 전에 커서를 앞당기지 않는다. 토큰 만료 또는 권한 범위 변경 시 기존 자료의 제공 정책을 재평가하고 전체 재수집한다.
3. 삭제와 권한 회수는 레코드뿐 아니라 검색 결과·요약·첨부 파생물에도 반영한다. 변화 탐지가 지원되지 않으면 완전한 전체 조회를 기준으로 비교한다.
4. [Graph의 429 처리](https://learn.microsoft.com/en-us/graph/throttling)를 참고해 지원 계약에 있는 Retry-After를 우선한다. 계약에 없는 헤더나 오류 의미는 추측하지 않는다. 401/403·계정 변경·브라우저 제어 해제는 일시 오류 재시도로 숨기지 않는다.
5. 결과 유실 후 쓰기를 재시도하려면 공급사가 보장하는 중복 방지 키 또는 원문 상태 조회가 필요하다. 현재 로컬 해시 중복 검사는 서버의 중복 상신 방지를 보장하지 않는다.

후속 구현에서 [정규화 페이지 수집 기반](sync-contract.md)과 합성 테스트 9개를 추가했다. 빈 중간 페이지·누락/중복·체크포인트 불일치·권한 회수·삭제·출력 실패를 검증하고 CLI로 전체 JSON을 게시한다. 실제 제품 커넥터, 서버 토큰 만료·HTTP 오류·변경 응답 유실 처리는 아직 미구현이다. 공급사 공개 근태 연동 문서와 ONE AI 안내를 검토했지만 조회 API 계약은 확보하지 못했다. [후속 검증](followup-verification.md)과 [HTML 분석](reference-review.html)을 참고한다.
