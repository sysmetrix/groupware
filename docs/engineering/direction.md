# GW 비서 평가와 지향점 (v0.77.0 기준, 2026-11-16)

커밋 144개, 문서, 소스·테스트 구조를 읽고 매긴 자체 평가다. 독립 평가가 아니며 실제 그룹웨어 화면에서의 동작은 이 평가에서 확인하지 않았다. 점수를 다시 매길 때는 이 문서의 날짜와 기준 버전을 함께 바꾼다.

## 1. 만들려는 것

**더존 Amaranth 10 그룹웨어 위에 얹는, 공공 재단 직원용 한 화면 AI 비서.**

| 의도 | 근거 |
|---|---|
| 한 화면에서 끝낸다 | 결재·메일·근태·예산·일정·자원·문서 찾기를 업무센터 하나로, 원래 화면은 오른쪽 처리 창에 |
| 사람이 마지막에 누른다 | 상신·결재·발송·삭제 클릭을 코드로 차단, 자동 입력은 상신 직전에서 멈춤, 확인 카드 |
| 거짓으로 말하지 않는다 | 허위 완료 금지, 확인 범위와 실패 표시 ([성공 기준](../ai-success-criteria.md)) |
| 설명 없이 쓴다 | [디자인 원칙](../design/principles.md) 다섯 가지 |
| 설치하면 알아서 굴러간다 | 확장 한 번 설치, SHA-256 대조 자동 업데이트, `npm run bump`와 배포 자동화 |

그 뒤에 동종 기관 판매라는 두 번째 목표가 있다([준비도 평가](../commercial/01-readiness-assessment.md)).

## 3. 지향점

**기능을 더하는 단계에서 증명하는 단계로 넘어간다.**

1. **핵심 여정 5개를 정하고 나머지는 동결한다.** 후보: 아침 홈 확인 뒤 결재 연속 처리 / 근태 신청 준비 / 결과보고 기안 / 예산 집행 조회 / 비서에게 묻기. 새 기능은 이 다섯에 걸릴 때만 받는다.
2. **출시 조건을 하네스 통과에서 실화면 스모크 통과로 올리고, 출시는 주 1~2회로 묶는다.**
3. **화면은 v0.76 디자인 원칙에서 고정한다.** 개편하지 않고 원칙 위반만 고친다.

### 작업 순서

| 단계 | 내용 | 올라가는 지표 |
|---|---|---|
| 0. 사실 맞추기 | README, 버전, 낡은 문서 머리말, 준비도 평가 (2026-11-16 완료) | 11, 3 |
| 1. 판매 가능 여부 확인 (사람이 병행) | 더존 약관과 재단 정보보안 담당 서면 확인. 불가면 목표를 내부 도구로 확정하고 `docs/commercial/` 작업을 멈춘다 | 13 |
| 2. 실사용 증거 (4주) | 1~3명 시범. 기기 안에만 남는 기능 사용 횟수·오류 기록과 내보내기. 주 1회 회수해 동결·수정 목록 갱신 | 5, 7, 10 |
| 3. 변경 내성 | 수집기 응답 모양 검사를 실화면 스모크에 넣고 어긋나면 해당 기능만 끄기. 선택자·라벨을 한 파일로 모으기. 둘러보기 대상 브라우저 E2E로 핵심 여정 5개 고정 | 12, 8 |
| 4. AI 평가 세트 | 실제 질문 50~100개에 기대 도구와 기대 거절을 적은 고정 문항. 로컬 라우터와 Gemini를 각각 채점. 개인정보 유출 문항 포함. 채팅 수정은 이 점수가 떨어지지 않을 때만 합친다 | 7, 6 |
| 5. 구조 정리 | `briefing.mjs`를 영역별 파일로(빌드가 이어 붙이므로 번들은 그대로), 테스트 파일을 버전명에서 영역명으로, `wc.css` 죽은 규칙 정리 | 9, 8 |

2~4가 본 작업이다. 5는 3의 E2E가 생긴 뒤에 한다(안전망 없이 177KB 파일을 쪼개지 않는다).

## 4. 작업 레벨별 에이전트 모델과 난도

| 레벨 | 작업 예 | 모델 | effort | 검증 |
|---|---|---|---|---|
| L0 탐색 | 파일 찾기, 호출처 조사, 변경 내역 요약 | Haiku | low | 없음 |
| L1 기계적 수정 | 문구, 토큰 값, 버전 올리기, 문서 머리말, 테스트 파일 이름 바꾸기 | Haiku | low~medium | `harness:fast` |
| L2 한 조각 안의 기능·버그 | 조각 파일 1~2개 범위 수정, 순수 함수와 테스트 추가, CSS 원칙 위반 수정 | Sonnet | medium | `harness:fast`, 해당 테스트, 둘러보기 확인 |
| L3 여러 조각에 걸친 기능 | 채팅 도구 추가, 예산·근태 판정 변경, 수집기 계약 변경, E2E 구축 | Opus | high | 전체 하네스, 실화면 스모크 |
| L4 안전·데이터 경계 | 비가역 차단, 기록기, 자동 업데이트·무결성, 저장소 이전, AI 전송 범위, 인증·토큰 | 가장 높은 모델(현재 Fable) | high~xhigh | 전체 하네스, 다른 모델의 독립 검토, 사람 확인 |
| L5 설계·평가 | 구조 분할 계획, 핵심 여정 선정, 준비도 재평가, 릴리스 전 종합 검토 | 가장 높은 모델, 계획 모드 | xhigh | 계획 승인 뒤 L2~L3로 내려 실행 |

운영 규칙:

- **레벨은 파일 크기가 아니라 닿는 경계로 정한다.** 아래 파일을 건드리면 한 줄 수정이어도 L4다.
  `src/live/wc/01-storage.js`, `19-draft-engine.js`, `20-recorder.js`, `21-governance.js`, `23-ai.js`, `31-chat-engine.js`, `33-chat-tools-act.js`, `src/live/collector.browser.js`, `src/live/ext/`, `scripts/live-build.mjs`(확장의 `mount.js`와 배포 묶음을 만든다).
- **독립 검토는 작성한 모델과 다른 모델로 한다.** L4와 릴리스 전 검토에만 쓰고, 검토자는 읽기 전용으로 둔다.
- **max effort와 다중 에이전트 전면 검토는 릴리스 묶음마다 한 번만 한다.** 버전마다 돌리면 수정 버전이 또 생긴다.
- **병렬 작성에는 파일 소유권 표를 먼저 만든다**([홈 구현 계약](../design/home/00-CONTRACT.md) 방식). 버전, 업데이트 내역, `16-events.js`는 메인 에이전트만 만진다.
- 같은 항목을 세 번 고쳐도 안 풀리면 한 레벨 올린다.
