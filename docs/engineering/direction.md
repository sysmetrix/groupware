# GW 비서 평가와 지향점 (v0.77.0 기준, 2026-11-16)

커밋 144개, 문서, 소스·테스트 구조를 읽고 매긴 자체 평가다. 독립 평가가 아니며 실제 그룹웨어 화면에서의 동작은 이 평가에서 확인하지 않았다. 점수를 다시 매길 때는 이 문서의 날짜와 기준 버전을 함께 바꾼다.

## 1. 만들려는 것

**더존 Amaranth 10 그룹웨어 위에 얹는, 공공 재단 직원용 한 화면 AI 비서.**

| 의도 | 근거 |
|---|---|
| 한 화면에서 끝낸다 | 결재·메일·근태·예산·일정·자원·문서 찾기를 업무센터 하나로, 원래 화면은 오른쪽 처리 창에 |
| 사람이 마지막에 누른다 | 상신·결재·발송·삭제 클릭을 코드로 차단, 자동 입력은 상신 직전에서 멈춤, 확인 카드 |
| 거짓으로 말하지 않는다 | 허위 완료 금지, 확인 범위와 실패 표시 ([성공 기준](../ai-success-criteria.md)) |
| 설명 없이 쓴다 | [디자인 원칙](../design/principles.md) 다섯 가지 |
| 설치하면 알아서 굴러간다 | 확장 한 번 설치, SHA-256 대조 자동 업데이트, `npm run bump`와 배포 자동화 |

그 뒤에 동종 기관 판매라는 두 번째 목표가 있다([준비도 평가](../commercial/01-readiness-assessment.md)).

## 3. 지향점

**기능을 더하는 단계에서 증명하는 단계로 넘어간다.**

1. **핵심 여정 5개를 정하고 나머지는 동결한다.** 후보: 아침 홈 확인 뒤 결재 연속 처리 / 근태 신청 준비 / 결과보고 기안 / 예산 집행 조회 / 비서에게 묻기. 새 기능은 이 다섯에 걸릴 때만 받는다.
2. **출시 조건을 하네스 통과에서 실화면 스모크 통과로 올리고, 출시는 주 1~2회로 묶는다.**
3. **화면은 디자인 원칙에서 고정한다.** (v1.23 방침 변경) 핵심 4(할 일 · 일정·예약 · 근태·연차 · 예산 집행)를 더 짧게 처리하게 만드는 구조 개편은 원칙 문서의 '메뉴 체계'·'홈' 절을 먼저 고친 뒤 한다. 그 밖의 화면 손질은 원칙 위반만 고친다.

### 운영자 기준 (2026-11-21, v1.11.0)

운영자의 지시 이력에서 뽑은 평가·개선 기준이다. 평가와 개선 항목을 고를 때 이 순서를 따른다.

1. **실제 업무 흐름이 바뀌는가**로 판단한다. 버전 수나 겨모양 손질은 성과가 아니다. 핵심 여정 5개를 실화면에서 마지막 버튼 직전까지 돌려 막힘을 찾는다.
2. **대상 화면은 PC 1366×768 이상**이다. 가장 빡빡한 노트북 화면(1366×768)을 기준으로 본다. 휴대폰·태블릿 배치와 화면낭독기 실사용 점검은 범위 밖이다(이미 넣은 것은 비용이 없어 유지하되 새로 능력을 들이지 않는다).
3. **숫자와 답은 정직해야 한다.** 같은 것을 가리키는 숫자는 어디서나 같고, 지난 자료를 최신처럼 보이지 않는다. 답은 물은 범위(기간·급한 것)부터 말한다.
4. **지적받은 한 곳만 고치지 않는다.** 같은 흐름 전체를 점검하고 연결된 문제를 함께 고친다.
5. **끝까지 마무리한다.** 머지·배포 뒤 실화면에서 다시 확인하고, 확인하지 못한 것은 그대로 적는다.

### 중간 점검 (v1.26.0, 2026-11-26)

점수는 여전히 다시 매기지 않았다(실사용 4주 기록이 아직 없다). 잰 사실만 적고, 지표가 움직인 방향을 표시한다.

| 지표 | 잰 것 (v0.79 → v1.26) | 방향 |
|---|---|---|
| 8 테스트·검증 | 단위 테스트 약 630 → 877건, 핵심 여정 34 → 48단계, 대화 문항 93 → 230개. 다만 여정에 '일정·예약'이 없고, 대화 문항은 규칙을 고친 쪽이 썼다 | 오름(과대평가 위험 있음) |
| 9 구조·유지보수성 | `briefing.mjs` 약 120KB → 130KB(분리 뒤 다시 자람), `wc.css` 133KB → 166KB, 조각 39 → 61개. **배포 번들 1,366,882 bytes / 상한 1,372,160 bytes(99.6%)** | 내림 |
| 10 개발 프로세스 | v1.11(11/21) 뒤 5일 동안 15개 버전. '출시는 묶어서' 규칙이 지켜지지 않음 | 그대로 낮음 |

가장 급한 것은 번들 예산이다. 여유가 약 5KB뿐이라 다음 기능이 들어오면 상한을 올리거나 무언가를 빼야 한다. 상한을 올리는 것은 `scripts/live-build.mjs`(L4) 변경이므로 2차 묶음에서 다룬다.

## 4. 작업 레벨별 에이전트 모델과 난도

| 레벨 | 작업 예 | 모델 | effort | 검증 |
|---|---|---|---|---|
| L0 탐색 | 파일 찾기, 호출처 조사, 변경 내역 요약 | Haiku | low | 없음 |
| L1 기계적 수정 | 문구, 토큰 값, 버전 올리기, 문서 머리말, 테스트 파일 이름 바꾸기 | Haiku | low~medium | `harness:fast` |
| L2 한 조각 안의 기능·버그 | 조각 파일 1~2개 범위 수정, 순수 함수와 테스트 추가, CSS 원칙 위반 수정 | Sonnet | medium | `harness:fast`, 해당 테스트, 둘러보기 확인 |
| L3 여러 조각에 걸친 기능 | 채팅 도구 추가, 예산·근태 판정 변경, 수집기 계약 변경, E2E 구축 | Opus | high | 전체 하네스, 실화면 스모크 |
| L4 안전·데이터 경계 | 비가역 차단, 기록기, 자동 업데이트·무결성, 저장소 이전, AI 전송 범위, 인증·토큰 | 가장 높은 모델(현재 Fable) | high~xhigh | 전체 하네스, 다른 모델의 독립 검토, 사람 확인 |
| L5 설계·평가 | 구조 분할 계획, 핵심 여정 선정, 준비도 재평가, 릴리스 전 종합 검토 | 가장 높은 모델, 계획 모드 | xhigh | 계획 승인 뒤 L2~L3로 내려 실행 |

운영 규칙:

- **레벨은 파일 크기가 아니라 닿는 경계로 정한다.** 아래 파일을 건드리면 한 줄 수정이어도 L4다.
  `src/live/wc/01-storage.js`, `19-draft-engine.js`, `19b-payment-goods.js`, `20-recorder.js`, `21-governance.js`, `23-ai.js`, `31-chat-engine.js`, `33-chat-tools-act.js`, `src/live/collector.browser.js`, `src/live/ext/`, `scripts/live-build.mjs`(확장의 `mount.js`와 배포 묶음을 만든다).
- **독립 검토는 작성한 모델과 다른 모델로 한다.** L4와 릴리스 전 검토에만 쓰고, 검토자는 읽기 전용으로 둔다.
- **max effort와 다중 에이전트 전면 검토는 릴리스 묶음마다 한 번만 한다.** 버전마다 돌리면 수정 버전이 또 생긴다.
- **병렬 작성에는 파일 소유권 표를 먼저 만든다**([홈 구현 계약](../design/home/00-CONTRACT.md) 방식). 버전, 업데이트 내역, `16-events.js`는 메인 에이전트만 만진다.
- 같은 항목을 세 번 고쳐도 안 풀리면 한 레벨 올린다.

## 5. 고도화 순환 (묶음 하나를 도는 법, v1.26.0부터)

기능을 하나씩 출시하지 않고 **묶음(wave)** 단위로 돈다. 묶음 하나가 출시 하나다.

| 단계 | 하는 일 | 누가 | 나오는 것 |
|---|---|---|---|
| 0. 기준선 | `npm run harness` 전체, 번들 bytes, 대화 문항 수·known 수, 내보낸 사용 기록 | 메인 | 기준선 표 |
| 1. 평가 (L5) | 3절 '중간 점검' 표를 새로 재고, 핵심 4와 안전 약속에 걸리는 빈틈만 고른다 | 메인, 계획 모드 | 후보 목록 |
| 2. 나누기 | 후보마다 레벨(4절)과 **파일 소유권 표**를 만든다. 겹치는 파일이 있으면 순서(DAG)로 묶는다. L4 파일이 낀 작업은 따로 표시한다 | 메인 | 소유권 표, 사람 승인 |
| 3. 병렬 실행 | 작업자마다 **따로 워크트리**를 준다(같은 트리를 쓰면 `build/live`를 서로 덮는다). 작업자는 자기 파일만 고치고, 자기 트리에서 전체 하네스를 돌린 뒤 자기 브랜치에 커밋한다. push·버전·업데이트 내역·`docs/`는 메인만 | 작업자 | 브랜치, 하네스 결과, 요청 목록 |
| 4. 합치기 | 통합 브랜치에 차례로 합치고, 합칠 때마다 `loop:once`, 끝에 `harness` 전체·`eval:chat`·`e2e`·둘러보기(밝게·어둡게·760px) | 메인 | 통합 하네스 보고서 |
| 5. 독립 검토 | L4가 낀 묶음은 작성자와 다른 모델이 읽기 전용으로 검토한다. 묶음마다 한 번 | 검토 작업자 | 발견 목록 |
| 6. 출시 | `npm run bump` 한 번, PR, 사람 확인 뒤 main. 머지 뒤 실화면 스모크, 못 본 것은 못 봤다고 적는다 | 메인 + 사람 | 버전 하나 |

작업자에게 주는 규칙:

- **평가 문항을 쓰는 작업자와 규칙을 고치는 작업자를 나눈다.** 같은 작업자가 둘 다 하면 점수가 실제 정확도를 말하지 못한다(3절 경과). 문항 작업자는 도구 정의만 보고 로컬 규칙의 정규식은 보지 않는다. 고치는 작업자는 `known: true` 문항을 규칙으로 풀고 문항의 기대 답은 바꾸지 않는다.
- **번들 예산을 작업 조건으로 준다.** 번들에 들어가는 파일을 고치는 작업자는 bytes 전후를 보고한다. 개발용 도구(보고서, 분석 스크립트)는 `scripts/`에 두어 번들에 넣지 않는다.
- 작업자가 화면 결함을 찾았는데 소유 파일 밖이면 고치지 않고 파일·줄·재현 순서로 보고한다. 메인이 다음 묶음 후보로 올린다.
- 작업자가 시작에 실패하면 원인이 바뀌었을 때만 다시 시작한다(예: 다른 에이전트로 바꿈). 같은 조건으로 되풀이하지 않는다.
