# 파일 자동화 오류와 복구

서버의 **데이터 연결** 화면에는 복구 방법·연속 실패 횟수·다음 확인 시각이 표시된다. `/api/automation`에는 `errorCode`, `runId`, `retryable`, `retryDelaySeconds`도 제공된다. `retryable`은 일시 오류의 간격 조절 대상이라는 뜻이며, `false`여도 수정된 파일을 찾기 위한 정기 확인은 계속된다. 정기 실행 중에는 다음 확인 시각이 비어 있다.

| 오류 코드 | 의미 | 조치 |
|---|---|---|
| INPUT_MISSING | 입력 파일 없음 | 설정 경로에 완전한 JSON 준비 |
| INVALID_INPUT | JSON·계약·크기 오류 | 필수 필드·UTF-8·크기 수정 |
| SOURCE_KIND | 합성 예제 등 부적합한 입력 출처 | 실제 내보내기 자료와 정확한 메타데이터 준비 |
| SCOPE_MISMATCH | 사용자 또는 조직 불일치 | 입력 범위와 설정 확인. 설정 변경 후 재시작 |
| STALE_SOURCE | 오래되거나 5분 초과 미래 자료 | 최신 자료를 다시 내보냄 |
| SOURCE_ROLLBACK | 현재 자료보다 과거인 내보내기 | 현재와 같거나 더 최신인 전체 자료 준비 |
| SNAPSHOT_CHANGED | 실행 중 다른 가져오기로 자료 변경 | 다음 확인에서 재검증 |
| IO_TEMPORARY | 파일 잠금·일시적 IO 오류 | 자동으로 확인 간격을 늘림 |
| STORAGE_UNAVAILABLE | 접근 거부·읽기 전용·공간 부족 | 자료 폴더 권한·공간 복구 |
| PROCESSING_FAILED | 분류되지 않은 처리 실패 | 자료와 실행 환경 확인 |
| AUDIT_UNAVAILABLE | 정기 실행의 실패 기록도 저장 불가 | 자료 폴더 쓰기 권한·공간 복구 |

오류 화면에는 임의의 운영체제 오류 문자열·스택·파일 내용이 노출되지 않는다. 감사 로그는 보고서 생성 완료와 실패 전환에 실행 ID를 붙이고 실패 원인을 코드로 남긴다. 동일 오류가 계속되면 같은 실패 로그를 반복 저장하지 않는다. 확인 성공 후 같은 오류가 다시 발생하면 새 실패 전환으로 기록한다.

## 확인 간격

기본 주기 60초에서는 일시 오류가 연속 발생할 때 **120 → 240 → 480 → 900초**로 다음 확인을 늦춘다. 상한은 `max(설정 주기, 900초)`이므로 원래 주기가 1시간이면 15분으로 단축하지 않는다. 입력/권한/공간 오류는 설정된 기본 주기를 유지한다. 성공하면 연속 실패 수와 대기 간격을 초기화한다. 서버 재시작 시 이 카운터도 초기화한다.

현재 실행이 끝나야 다음 타이머를 등록하므로 겹치는 정기 실행을 만들지 않는다. 수동 실행은 대기 시간을 건너뛰지만 이미 실행 중이면 같은 작업을 기다린다. 수동 실행이 기존 타이머의 시각을 다시 예약하지는 않는다. 중지하면 다음 실행을 취소하며 이미 시작한 파일 작업은 끝까지 진행한다.

## 자료와 보고서 보호

- 같은 사용자·조직·출처의 `exportedAt`이 현재보다 과거이면 자동 교체하지 않는다. 시각이 같다고 내용 동일성을 보장하지는 않는다. 출처와 시각은 파일 작성자가 제공한 값이다.
- 저장된 보고서는 재시작 후 입력 파일 검증이 성공해야 제공된다. 입력 파일이 없거나 손상되면 디스크에 보고서가 있어도 다운로드를 거부한다.
- 검증 성공 뒤 입력 파일이 다시 바뀌면 다음 확인에서 감지한다. 매 HTTP 다운로드마다 입력 파일을 다시 읽는 구현은 아니다.
- 파일 검사 중·오류 발생·날짜 변경·자료 만료·스냅샷 변경 시 현재 보고서를 제공하지 않는다. 보고서 생성 도중 자료 변경도 확인한다.
- 보고서와 감사 기록은 별도 파일이다. 프로세스 중단 시 양쪽의 원자적 커밋·정확히 한 번 실행·누락 감사 기록 복원은 보장하지 않는다.

이는 로컬 파일 처리 정책이다. HTTP Retry-After, 서버 작업 재시도, 증분 수집, 다중 PC 작업 분산은 구현되지 않았다. [공식 레퍼런스 분석](reference-review.html)에서 이후 설계를 구분한다.
